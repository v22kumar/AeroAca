# Local lab: running the academy's code on your own PC

The lessons marked **Run it yourself** and the portfolio's **Build it** steps are small programs you build and run locally. Every one of them lives in this repository under `labs/`, with the exact command and the output you should see. The academy's CI builds and runs all of them on every change (`tests/labs.test.ts`), so when a lesson shows an expected output, that output was produced by that program, not typed in.

Nothing runs in the browser: there is no C compiler or Python there without a heavy or paid dependency, and the academy stays free and offline-capable. The trade is ten minutes of one-time set-up.

## What you need

| Tool | Why | Check it works |
|---|---|---|
| A C compiler: gcc or clang | The C labs and the portfolio detection function | `gcc --version` or `clang --version` |
| make | The portfolio Makefile (optional elsewhere) | `make --version` |
| Python 3.10 or newer | The Python labs and the sensor model | `python3 --version` (on Windows often `python --version`) |
| git (recommended) | To clone the repository and keep your own copies | `git --version` |

### Windows

The simplest route is **WSL** (Windows Subsystem for Linux): install Ubuntu from the Microsoft Store, then in the Ubuntu terminal run `sudo apt update && sudo apt install build-essential python3 git`. Everything below then works exactly as written. Without WSL: install MSYS2 or MinGW-w64 for gcc and make, and Python from python.org (tick "Add to PATH"); in that case the command is `python` rather than `python3`, and `./bits` becomes `bits.exe`.

### macOS

`xcode-select --install` provides clang (gcc is an alias to it) and make. Python 3 comes with recent macOS or from python.org or Homebrew.

### Linux

`sudo apt install build-essential python3 git` (Debian/Ubuntu) or the equivalent for your distribution.

## Getting the files

```
git clone https://github.com/v22kumar/AeroAca.git
cd AeroAca/labs
```

or download the repository as a zip from GitHub and unzip it. Each lab is one folder with one source file, so you can also copy the code from the lesson page (the Copy button) into a new file with the name shown.

## Running a lab

Open a terminal **in the lab's folder** and run the command shown on the lesson page, for example:

```
cd labs/c/bits
gcc -std=c11 -Wall -Wextra -o bits bits.c && ./bits
```

Compare your output with the lesson's "Expected output" block line by line. If the compiler reports warnings, read them; the labs compile clean with `-Wall -Wextra`, so a warning means a change you made. Then do the "Try next" change, predict the result, and run again.

## Verifying the whole set at once

From the repository root, `node scripts/sync-labs.mjs --check` rebuilds and reruns every lab and reports whether any output differs from what the lessons show (it needs Node.js, which the app itself needs). `npm test` does the same inside the test suite.

## The STM32 path (documented, not verified in CI)

The host labs prove logic. Running on the board needs a toolchain and hardware the academy's build environment does not have, so this part is **documented from the vendor's instructions and not executed in CI**:

1. Install **STM32CubeIDE** (free, from st.com; an account is required to download). It includes the arm-none-eabi GCC toolchain, CubeMX for pin and clock configuration, and the ST-LINK debugger support.
2. Any **Nucleo** board (for example NUCLEO-F401RE or NUCLEO-F446RE) has an on-board ST-LINK, so a USB cable is the only extra. The portfolio's hardware path also needs a TMP102 (or similar I2C temperature sensor) breakout and a USB-serial adapter or the Nucleo's virtual COM port.
3. Create a project for your board in CubeIDE, enable I2C1, USART2 and IWDG in CubeMX, generate code, and add `detect.c`/`detect.h` from `labs/portfolio` to `Core/Src` and `Core/Inc`. The detection function is hardware-free and compiles unchanged; the first-STM32 lesson walks through the rest.
4. Build (hammer icon), flash and debug (bug icon). The debugger stops at `main`; press resume.

If a step on the board does not match the lesson, the lesson is wrong or your board differs; either way, say so in your notes rather than ticking the deliverable.

## Rules the labs follow

- Deterministic: no random numbers, no clock reads in the output, so two runs print the same text.
- Standard C11 and the Python standard library only; no packages to install for the labs themselves (PyVISA and pyserial are needed only for the bench, and the lessons say so).
- Each lab fits on one screen and does one thing the lesson taught.
- The expected output is regenerated by running the program (`node scripts/sync-labs.mjs`), never edited by hand.
